1. 背景与瓶颈

M3/M4 的 runtime_events: Arc<Mutex<UnboundedReceiver>> 被 turn_start 在整个 turn 期间持锁 drain（http_server.rs 原 let mut rx = st.runtime_events.lock().await）。这把所有租户、所有用户的 turn 全局串行——一个长 turn（如停在审批上等人决策）会阻塞所有其他 turn。M4 的 max_concurrent_turns 门控只能 429 拒绝，不能真并发。

M5 引入 DriverPool：N 个独立 driver 线程，各持一个 app-server 进程 + 独立 event 通道。turn_start acquire() 一个空闲 slot，独占 drain 该 slot 的 event_rx（无共享 mutex），turn 结束 release()。

2. 设计要点

  • free-list 队列调度：tokio unbounded channel 作空闲 slot 队列。acquire 从 free_rx.recv().await 取 idx 并 take 出该 slot 的 event_rx；DriverGuard::Drop 把 event_rx 放回 + idx 入 free 队列。无需扫描。
  • AtomicI64 全局 approval_id：N 个 driver 各 fetch_add 同一 Arc<AtomicI64>，跨 slot 生成 id 全局唯一连续（M3 per-driver 计数器在多 driver 下会碰撞）。
  • turn_slots 路由：Arc<Mutex<HashMap<i64,usize>>>（turn_db_id→slot idx）。approval_resolve/interrupt/ws-revoke 经 ticket.turn_id 查 slot，driver_pool.cmd_tx(idx) 路由到持该 turn 的 driver。
  • 向后兼容：pool_size=1 等价 M4 单 driver。

6. 零回归结论

M5 的 DriverPool 在 pool_size=1 时与 M4 单 driver 行为等价；pool_size≥2 时启用真并发，且：

  • M3 HITL 审批桥（requested→park→resolve/interrupt）完全不变，仅 resolve/interrupt 改为经 turn_slots 路由到正确 slot；
  • M4 计量（usage_records 落库 + cost 推导 + 聚合 API + 并发门控 429）完全不变；
  • SIMULATE 测试模式 + 合成 tokenUsage 注入完全不变；
  • driver_loop 内部逻辑（spawn/initialize/thread_start/turn_start/drain/park）零改动，仅 approval_id 取值改 AtomicI64 fetch_add。
