§0 执行摘要

仓库规模：Cargo workspace + Bazel overlay，111+ Rust crate（105 workspace member + 14 ext/ 子目录），Rust 2024 edition + Tokio 异步运行时。
架构本质：Codex Harness 是「单用户、本地、可打断的 Agent 引擎」。核心引擎层 codex-core 驱动 Turn 七阶段循环，通过 app-server JSON-RPC 协议层对外暴露 Thread/Turn/Item 三原语，底层以 SQLite + JSONL rollout 实现本地持久化，以 execpolicy（Starlark）+ 三平台 OS 沙箱实现命令级隔离。
核心结论：Harness 提供了完备的 Agent 执行内核与协议接口，但缺失多租户、计量、审计、云端会话、跨进程审批等企业能力。Nexus 路径：控制/执行分离——以 app-server 为唯一集成面，消费事件流写云端 Postgres，下发 config.toml + execpolicy 规则集表达租户差异，不改内核，四重隔离保障安全。

3.2 JSON-RPC 2.0 协议设计

类 JSON-RPC 2.0 但不发送 "jsonrpc":"2.0" 字段（rpc.rs:1-2 注释："We do not do true JSON-RPC 2.0"）。JSONRPCMessage 为 untagged 枚举，区分 Request/Notification/Response/Error。RequestId 支持 String/Integer。可选携带 W3C trace 分布式追踪上下文。

v1 vs v2 是协议 API 版本划分：v1 保留旧稳定类型；v2 是新 API 命名空间，所有类型 #[ts(export_to = "v2/")]，用 #[experimental("...")] 标注未稳定方法。

5.5 单租户命令级 vs 多租户隔离

上述所有 crate 实现的是单进程、单租户、命令级隔离。PermissionProfile、Policy 均为进程级配置，不携带 tenant 身份。在 Nexus 中这些属于数据平面执行器：控制平面负责租户认证/配额/调度；沙箱/execpolicy 在执行器内部保证单条命令不越权。core/src/sandboxing/mod.rs 的 ExecRequest（mod.rs:50-74）就是控制平面下发的执行单元边界。

6.3 responses-api-proxy

极简 HTTP 代理（lib.rs:73-275）：特权用户持 key，非特权用户通过 HTTP 调用。只允许 POST /v1/responses。硬核安全：栈缓冲 + zeroize + mlock(2) 防止 key 落盘交换。--dump-dir 采集 request/response pair。这是 Nexus "自建 Model Gateway" 的本地单租户极简形态。

6.4 云控制平面

backend-client：PathStyle（client.rs:117-133）区分 CodexApi（/api/codex/...）与 ChatGptApi（/wham/...）。覆盖 list_tasks、create_task、get_config_bundle（enterprise-managed TOML）、get_rate_limits。

cloud-config：启动 15s 超时加载，miss 时最多 5 次重试，后台每 15 分钟刷新，401 触发 auth recovery。cloud_config_eligible_auth 只对 business/education/Enterprise plan 启用。

6.5 登录与认证流程

login crate 统一管理凭证：CodexAuth 枚举变体包括 ApiKey、Chatgpt、ChatgptAuthTokens、Headers、AgentIdentity、PersonalAccessToken、BedrockApiKey、BedrockAccessKeys。AuthManager 持有 shared 状态，auth() async 返回当前凭证，unauthorized_recovery() 用于 401 后刷新。OAuth Device Code Flow + PKCE 在 device_code_auth.rs 实现。

数据流：模型选择 config.toml → merge_configured_model_providers → ModelProviderInfo → create_model_provider → ModelProvider → ResponsesClient。Auth：codex login → AuthManager → CodexAuth → api_auth_for_scope → SharedAuthProvider → header 注入。Bedrock：AwsAuthContext::sign 做 SigV4。

6.6 GPT-5.x 不开源的影响

CLAUDE.md 明确："Codex did not open-source the model." Harness + 集成接口开源，但 GPT-5.x 是 API/ChatGPT-only。本地/私有模型通过 ollama/lmstudio 路由（能力受限）。Nexus 需自建 Model Gateway 实现：多模型路由、Token 计量与配额、租户级路由隔离、审计日志。

§10 Nexus 落地启示

10.1 控制/执行分离

最关键设计判断：Codex Harness 是「单用户、本地、可打断的 Agent 引擎」；Nexus 要建的是「让这台引擎变成多租户、可计量、可审计、崩溃不丢会话的企业服务」。控制面长期有状态、多租户、强一致；执行面无状态、一次性、可随时销毁。仅经 app-server 协议与对象存储通信。

10.2 app-server 集成

  • 唯一集成面：通过 app-server JSON-RPC 集成，不通过 codex exec 或 in-process SDK
  • Thread 生命周期：消费 thread/turn/item 事件流
  • 审批桥接：消费 Server→Client 审批请求，持久化到 DB，在 thread/resume 时回放
  • Thread 操作：thread/start/resume/fork/revert 支持会话恢复、分支、回退

10.3 会话云端化

  • 控制面消费 app-server 事件流 → Postgres（权威元数据）
  • rollout JSONL 同步到对象存储（可重建的执行态）
  • ThreadStore trait 屏蔽本地/云端差异
  • Pod 死亡：从 Postgres 恢复元数据 → 从对象存储拉 rollout → thread/resume 重建

10.4 execpolicy 承接策略

  • 控制平面为租户生成 overlay 规则文件（Starlark）
  • 执行器加载 overlay → merge_overlay 到基础 policy
  • Policy::check 评估 allow/prompt/deny
  • RequirementsExecPolicy 可序列化，跨控制平面/执行器传输

10.5 不改内核

  • 上游日均 10+ commit、111+ crate——修改内核导致 merge 冲突无法收口
  • 租户/角色差异表达为生成的 config.toml + execpolicy 规则集
  • 事件桥接消费 app-server 事件流
  • 不可避免的内核 patch 放 patches/ + 上游追踪看板

10.6 四重隔离

隔离层机制对应 crate

OS 沙箱层Seatbelt / Landlock+seccomp+bubblewrap / Windows tokensandboxing, linux-sandbox, windows-sandbox-rs

报告总结：Codex Harness 提供了完备的 Agent 执行内核（Turn 七阶段 + 五原语）、成熟的 JSON-RPC 协议层（双向事件流 + 协议级审批）、可靠的本地持久化（SQLite 镜像 + JSONL rollout）、强力的命令级安全（execpolicy + 三平台 OS 沙箱）和灵活的扩展机制（贡献者矩阵）。Nexus 落地路径：以 app-server 为唯一集成面，消费事件流写云端 Postgres，下发 config.toml + execpolicy 表达租户差异，不改内核，四重隔离保障安全。核心自建项：多租户控制平面（L1-L3）、执行面托管外壳（L4）、Model Gateway（L6）、存储与治理（L7）。
