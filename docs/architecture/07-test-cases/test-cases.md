# Nexus 系统测试用例与验收标准

> 维度 07 · 系统测试用例与验收标准 | 对齐路线图 §7 各阶段验收 + §8 反模式 | 遵循 AGENTS.md 测试规范

## 1. 测试分层体系

Nexus 平台采用九层测试体系，自底向上覆盖从代码单元到合规审计的全链路质量。每层有明确的工具链、运行策略和退出条件。

### 1.1 单元测试（Unit）

| 维度 | 说明 |
|---|---|
| 定位 | Rust `*_tests.rs` 模块级测试，验证单个函数/结构体/算法分支 |
| 工具 | `pretty_assertions::assert_eq`（深比较，清晰 diff）；`#[cfg(test)] #[path = "xxx_tests.rs"]` 外置测试文件 |
| 规范 | 不修改 `process` 环境变量（AGENTS.md: "Avoid mutating process environment in tests"）；不新建仅测一次的 helper 方法；对整个对象做 `assert_eq`，不逐字段比较 |
| 关键 crate | `codex-core` 内 `run_turn` 状态机分支、`execpolicy` 规则解析器 parser/evaluator、`apply-patch` 流式解析器、`linux-sandbox` Landlock 规则生成 |
| 运行 | `just test -p <crate>`；禁止直接 `cargo test` |
| Nexus 自建 | 控制平面 L3（身份租户/策略中心/配额计费）核心逻辑、事件消费者幂等写入器、配置生成器 execpolicy 规则集编译 |

### 1.2 集成测试（Integration）

| 维度 | 说明 |
|---|---|
| 定位 | `core/suite` 或 `app-server/tests/suite` 下的端到端 Agent 行为测试 |
| 工具 | `test_codex`（构建测试 Codex 实例）、`mount_sse_once`（mock SSE 响应服务器）、`responses::sse` / `ev_*` 构造事件流、`wait_for_event`（优于带 timeout 的变体） |
| 规范 | agent 逻辑变更 MUST 新增集成测试（AGENTS.md 强制）；优先 `mount_sse_once` 而非 sequence/match 变体；`ResponseMock` 保留以断言 outbound POST body |
| 关键 crate | `app-server/tests/suite/v2/` 下 `turn_start.rs`、`thread_start.rs`、`thread_resume.rs`、`thread_fork.rs`、`compaction.rs`、`turn_interrupt.rs` |
| 典型模式 | `let mock = responses::mount_sse_once(&server, responses::sse(vec![ev_response_created, ev_function_call, ev_completed])).await;` → `codex.submit(Op::UserTurn{...}).await?;` → 断言 `mock.single_request()` |
| Nexus 自建 | 事件桥接消费者集成测试（事件流→Postgres 落库）、审批桥接集成测试（拦截→落库→回写→继续）、配置生成器集成（角色→config.toml+execpolicy 生成并验证） |

### 1.3 快照测试（Snapshot）

| 维度 | 说明 |
|---|---|
| 定位 | `insta` crate 快照，覆盖 TUI 用户可见输出和结构化文本渲染 |
| 工具 | `cargo insta` CLI；`*.snap.new` 文件审查流程；`cargo insta accept` 接受 |
| 规范 | 任何影响用户可见 UI 的变更 MUST 附带快照覆盖（AGENTS.md 强制）；先 `just test -p codex-tui` → `cargo insta pending-snapshots` → 逐文件审查 → `cargo insta accept` |
| 关键 crate | `codex-rs/tui/tests/suite/` 下 `status_indicator.rs`、`reconnect.rs`、`focus_palette.rs`、`resize_reflow.rs`、`vt100_history.rs` |
| Nexus 自建 | Web 门户时间线渲染快照、审批卡片渲染快照、IM 消息卡片渲染快照 |

### 1.4 协议测试（Protocol）

| 维度 | 说明 |
|---|---|
| 定位 | app-server JSON-RPC 2.0 协议端到端验证 + TS/JSON Schema 漂移检测 |
| 工具 | `app-server-test-client`（loopback 响应服务器）、`TestAppServer::builder().build()` + `send_thread_start_request_with_auto_env()`、`just write-app-server-schema`（schema 固件生成）、`just write-config-schema` |
| 规范 | v2 API 开发遵循 `*Params`/`*Response`/`*Notification` 命名；camelCase 序列化；`#[ts(export_to="v2/")]`；禁止 `skip_serializing_if`；`just test -p codex-app-server-protocol` 验证 |
| 关键测试 | `app-server/tests/suite/v2/` 下 `initialize.rs`、`thread_start.rs`、`turn_start.rs`、`thread_resume.rs`、`connection_handling_websocket_unix.rs`、`output_schema.rs` |
| Schema 漂移 | `generate-ts` / `generate-json-schema` 产出与 `schema_fixtures` 对比；CI 检测未重新生成 schema 的 PR 阻断 |
| Nexus 自建 | 控制面↔沙箱 Pod 的 app-server 代理层协议测试（thread/start → 事件流 → thread/resume 全链路 JSON-RPC 验证） |

### 1.5 端到端测试（End-to-End）

| 维度 | 说明 |
|---|---|
| 定位 | PoC 三大假设验证 + 关键跨层场景验证 |
| 三假设 | ①事件流不阻塞 Harness ②thread/resume 跨 Pod 可靠 ③审批跨进程持久化回写 |
| 工具 | K8s kind 集群 + 真实 Pod 调度 + wiremock mock 模型端点 + Postgres 落库验证 |
| 退出条件 | M0 三假设全部 Go；任一 No-Go 则架构方案需重设计 |
| Nexus 自建 | 一次任务完整 13 步生命周期端到端（提交→鉴权→调度→启动→采样→事件→落库→审批→执行→压缩→产物→结算→销毁） |

### 1.6 安全测试（Security）

| 维度 | 说明 |
|---|---|
| 定位 | 跨租户越权演练 + 提示注入 + 供应链 + 沙箱逃逸 |
| 频率 | 季度红队演练（M10 前建立体系，M10 后常态化） |
| 范围 | ①提示注入（不可信内容不得改变系统策略）②跨租户越权（RLS + 网络策略 + 密钥 + 存储四重取证）③供应链（依赖/MCP 连接器/镜像）④沙箱逃逸（Seatbelt/Landlock+seccomp/bwrap） |
| 工具 | 自建越权测试套件（租户 A 凭据尝试访问租户 B 数据）；沙箱出站验证脚本；镜像扫描（trivy/grype）；凭据泄露扫描 |
| 关联反模式 | "用 LLM 判断权限够不够"（§8.1）、"只做逻辑隔离"（§8.1）、"把 API Key 打进沙箱镜像"（§8.1） |

### 1.7 评测体系（Evaluation）

| 维度 | 说明 |
|---|---|
| 定位 | Agent 质量回归门禁，不是传统 QA，而是"证明这次升级变好了还是变差了"的迭代权 |
| 三类数据集 | 黄金集（主路径 happy path）、对抗集（越权/注入/工具失败/数据缺失 edge case）、生产采样集（脱敏后真实流量） |
| 五评测平面 | ①任务完成率 ②工具调用正确率 ③安全拦截率 ④成本/任务 ⑤体验（步骤效率、澄清次数） |
| CI 门禁 | 模型/提示/工具/策略任一变更 MUST 跑全量评测回归；评测滞后于功能 = 失去迭代权 |
| 退出条件 | M8：变更前回归通过 + 失败任务可定位到 LLM/tool/data/policy 层 |
| Nexus 自建 | 评测数据集管理、评测 runner、五平面看板、CI 回归 pipeline |

### 1.8 性能测试（Performance）

| 维度 | 说明 |
|---|---|
| 定位 | 并发承载、冷启动、P95 时延、事件流吞吐 |
| 指标 | 100+ 并发任务无级联失败；冷启动 < 5s；P95 时延达标；事件流吞吐无背压 |
| 工具 | k6 / wrk 负载注入；OTel trace 链路；Prometheus 指标采集 |
| 关键路径 | 网关→控制面→调度→Pod 启动→app-server 连接→首次响应（冷启动全链路） |
| Nexus 自建 | 预热池策略验证、并发调度优化验证、队列优先级验证 |

### 1.9 合规测试（Compliance）

| 维度 | 说明 |
|---|---|
| 定位 | 审计完整性、WORM 不可篡改、RLS 跨租户 0 泄露、沙箱自检 |
| 指标 | 审计字段完整率 ≥ 99.9%；WORM 不可篡改（写入后不可修改/删除）；RLS 跨租户 0 泄露；沙箱自检清单全通过 |
| 工具 | 审计字段覆盖率检测脚本；WORM 存储篡改尝试；RLS 穿透测试（构造不同租户上下文执行 SQL）；沙箱自检脚本（Landlock/seccomp 生效验证） |
| 关联反模式 | "审批状态存在 Harness 里"（§8.1）、"会话只存本地 rollout"（§8.1） |

## 2. 关键测试用例矩阵

以下为 P0 级核心测试用例，每条包含用例 ID、标题、前置条件、步骤、预期结果、优先级、所属阶段。

### TC-001 会话落库幂等（thread_id + turn_id + item_seq 重复丢弃）

| 字段 | 值 |
|---|---|
| 用例 ID | TC-001 |
| 标题 | 事件流落库幂等：同一 thread_id + turn_id + item_seq 的重复事件写入被丢弃 |
| 前置条件 | Postgres 核心表已建（thread/turn/item）；事件消费者运行中；mock app-server 产生 SSE 事件流 |
| 步骤 | 1. 启动一个 thread，产生 turn T1，事件流包含 item_seq=1,2,3 |
| | 2. 消费者写入 Postgres（3 条 item） |
| | 3. 重放同一事件流（模拟 Pod 重启后重新消费） |
| | 4. 查询 item 表 WHERE thread_id=X AND turn_id=T1 的记录数 |
| 预期 | item 表仅 3 条记录，重复写入被幂等丢弃（UNIQUE 约束或 INSERT ON CONFLICT DO NOTHING） |
| 优先级 | P0 |
| 所属阶段 | M0（PoC 事件桥接验证） |

### TC-002 seq 缺口补齐（item_seq 不连续时自动补齐或标记缺口）

| 字段 | 值 |
|---|---|
| 用例 ID | TC-002 |
| 标题 | 事件流 item_seq 缺口检测与补齐 |
| 前置条件 | 事件消费者已实现 seq 缺口检测逻辑 |
| 步骤 | 1. 启动 thread，turn T1，事件流为 item_seq=1,2,4,5（缺 3） |
| | 2. 消费者检测到 seq=3 缺失 |
| | 3. 标记缺口并触发补齐请求（从 app-server rollout 重放缺失 item） |
| | 4. 验证 item 表最终有序且完整 |
| 预期 | 缺口被检测、记录、补齐；item 表最终包含 seq=1-5 全部记录 |
| 优先级 | P0 |
| 所属阶段 | M0→M2 |

### TC-003 thread/resume 跨 Pod 恢复

| 字段 | 值 |
|---|---|
| 用例 ID | TC-003 |
| 标题 | Pod 销毁后新 Pod 从云端状态恢复会话（thread/resume） |
| 前置条件 | thread T1 已在 Pod-A 上运行并产生 5 个 item；rollout 已上传对象存储；Postgres 有完整事件 |
| 步骤 | 1. 销毁 Pod-A（模拟崩溃/回收） |
| | 2. 调度新 Pod-B |
| | 3. Pod-B 下载 rollout 到本地 |
| | 4. 调用 `thread/resume` 恢复会话 |
| | 5. 在 Pod-B 上继续提交 turn T2，产生新 item |
| | 6. 查询 Postgres 验证 T1 的 5 个 item + T2 的新 item 均存在 |
| 预期 | 跨 Pod 恢复成功，历史 item 不丢失，新 turn 可继续追加 |
| 优先级 | P0 |
| 所属阶段 | M0（PoC 三假设之二） |

### TC-004 审批跨小时 Pod 重建后重放决策

| 字段 | 值 |
|---|---|
| 用例 ID | TC-004 |
| 标题 | 审批请求落库后 Pod 重建，用户决策回写后任务继续 |
| 前置条件 | 审批中心已实现（ApprovalTicket 生命周期管理）；审批请求先落 DB 再推送用户 |

| 预期 | 审批不丢失；跨 Pod 跨小时可恢复；决策先落库后回写，宕机可重放 |
| 优先级 | P0 |
| 所属阶段 | M0（PoC 三假设之三）→ M3（审批中心正式版） |

### TC-008 预算熔断优雅暂停

|---|---|
| 用例 ID | TC-008 |

### TC-011 compact 前后上下文可回溯

| 字段 | 值 |
|---|---|
| 用例 ID | TC-011 |
| 标题 | 上下文压缩前完整上下文已落云端，compact 后可回溯 |
| 前置条件 | 事件落库已包含完整 item 流；compact 触发条件已配置（token 阈值） |
| 步骤 | 1. 持续提交 turn，上下文接近 token 阈值 |
| | 2. Harness 触发 auto compact（`run_auto_compact`） |
| | 3. 验证：压缩前的完整 item 列表已写入 Postgres（事件流已消费） |
| | 4. compact 后上下文缩短，继续提交 turn |

## 6. 测试工具链与 CI 集成

### 6.1 Rust 测试工具链（遵循 AGENTS.md）

| `just fix` | Clippy linter 修复 | `just fix -p <crate>` |
| `just fmt` | 代码格式化 | `just fmt` |
| `pretty_assertions` | 测试断言（清晰 diff） | `use pretty_assertions::assert_eq;` |
| `insta` | 快照测试 | `cargo insta accept -p <crate>` |
| `just bench` | 性能基准（divan） | `just bench` 或 `just bench-smoke` |
| `mount_sse_once` | mock SSE 响应 | `responses::mount_sse_once(&server, responses::sse(vec![...]))` |
| `wait_for_event` | 等待事件 | `wait_for_event(&codex, "turn/completed").await` |
| `TestAppServer` | app-server 集成测试 | `TestAppServer::builder().build()` |
| `just write-app-server-schema` | schema 固件生成 | CI 检测漂移 |
| `just write-config-schema` | 配置 schema 生成 | CI 检测漂移 |

### 6.3 CI 门禁策略

| 触发条件 | 必跑测试 | 阻断条件 |
|---|---|---|
